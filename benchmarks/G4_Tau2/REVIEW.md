## Claims and mechanisms

The paper models separate agent/customer databases plus shared history as a Dec-POMDP. Separate tools reveal different observations; synchronization propagates cross-side effects such as provider roaming permission, data quota, and bill payment. Atomic tasks contain initialization, solution actions and assertions, allowing composition and deterministic verification. Appendix A supplies personas and default/solo trajectories; B describes implementation/task review; C defines turn-taking and grounded user prompts; D supplies policies/workflows; E describes user errors.

The claimed Default versus No-User gap is a diagnostic comparison, not pure causal isolation of communication: tool ownership, policy wording and accessible task information also change. Oracle Plan reduces planning difficulty while exposing the reference solution and therefore must remain a separate setting. Temperature zero does not remove provider or user-simulator variability. The paper uses four trials per task and dated model snapshots, including `gpt-4.1-2025-04-14` as user simulator. None of those model claims was tested here.

Prior-work boundaries: τ-bench already contributes Tool-Agent-User customer-service evaluation and pass^k reliability. ToolSandbox already has stateful tool evaluation; FlowBench studies explicit workflow knowledge; IntellAgent builds synthetic policy-driven tests; APIGen-MT generates linked conversational tool trajectories. The defensible distinction here is the customer also acting through constrained tools on a coupled world, combined with compositional telecom tasks and controlled ablations. We did not perform an exhaustive novelty search beyond the paper's cited primary work, and do not claim that Dec-POMDPs or invariant checking originate here.

## Verified contracts and deviations

1. **Reward basis matters.** Section 3.3 describes telecom as using assertion functions but does not explain the released ACTION exceptions. The original released main set actually has 94 assertion-only tasks and **20 tasks with ENV_ASSERTION + ACTION**. The 20-task small set has 18 + 2. A selected locked-SIM task needs transfer: state-only reward is 1 even for no-op; complete official reward is 0 until transfer is performed. This explains why the official ACTION exception is necessary for premature transfer termination, as discussed in Appendix E. This is not an official false acceptance: only the intentionally isolated environment component accepts no-op; the complete official reward rejects it.
2. **History is executable evidence.** `Environment.set_state` replays initialization plus tool-call/response pairs, enforces response identity/content consistency, then synchronizes the databases. A fabricated success message is insufficient. Corrupted recorded responses and nonexistent-phone state initializations were rejected in every selected configuration.
3. **DB equality is not always the selected objective.** The evaluator computes hashes for both databases, but includes DB reward only when DB is in the task's reward basis. Telecom assertions can accept multiple valid end states. Raw DB checks must not be substituted for configured task success.
4. **Premature termination overrides success.** The full upstream evaluator returns zero for MAX_STEPS and TOO_MANY_ERRORS, even after reference actions reach the intended state. We verified 24 such overrides.
5. **Action checking is coarse.** Source inspection shows expected actions are matched by name/argument subsets, without ordering, multiplicity or requestor equality in `compare_with_tool_call`. With `compare_args=None`, keys come from the predicted arguments, so missing expected arguments are not independently required by that comparison. Executable environment replay still constrains callable arguments. These are scope limitations, not a demonstrated model exploit.
6. **Later versions are different protocols.** [v0.1.3](https://github.com/sierra-research/tau2-bench/releases/tag/v0.1.3), `5ba9e3e56db57c5e4114bf7f901291f09b2c5619`, makes ALL skip NL assertions and adds ALL_WITH_NL_ASSERTIONS. Original ALL calls the NL evaluator before selecting reward components, so an optional diagnostic could incur judge calls even without contributing to reward. Selected telecom cases have no NL assertions; no judge was called. The evaluator-only source diff is retained without task solutions.
7. Current main was independently pinned to `122e2432b82d740e8f313f46f0a071729c404f39`. Its README describes τ-bench 2.0, six languages, voice, replacement task sets and changed judges. v1.0/v1.0.1 belong to the τ³ era. Neither is a substitute for this original pin. Current-release audit here is static, not execution.

## Evidence and limits

`results/calibration.json` is a numeric projection, with raw reference trajectories retained privately under `PUBLICATION.md`: six preselected official small tasks × two tool configurations × five controls = 60 rows. Twelve reference replays achieve configured deterministic reward 1; twelve no-ops and twelve drop-last-action controls achieve 0; twelve corrupted responses and twelve invalid initial states raise expected ValueError. For the three one-action tasks, drop-last-action equals no-op and is not an independent near-success condition. Near-success is an operational label, not proof of semantic closeness.

`results/full-reward.json` is also a numeric projection: 36 nominal trajectories agree with the official ALL aggregator; 24 reference trajectories with failure termination receive 0. Official tests: six environment tests and 49 telecom tool tests pass. `results/metrics-formulas.json` checks 642 exact combinatorial identities, not model performance. There are no task timeouts; the first calibration process failed on missing pandas before any task execution, was retained, and was rerun after isolated dependency installation.

All six small-task IDs are absent from the 114-task main set. Accordingly this is evaluator calibration, not a representative score or exact paper reproduction. The offline `results/reward-basis-inventory.json` and `scripts/recount_inventory.py` expose only task IDs/component labels and allow recounting the 20/114 ACTION exceptions without task answers or network. The main/full dataset hashes are pinned but no main-set live evaluation occurred. Latest compatible minimal dependencies, rather than the full historical PDM lock environment, were used and frozen. Paper model snapshots, policy comparisons, persona effects, simulator error rates and performance gaps remain **not_run**. No uncertainty interval is assigned to deterministic fixtures; model pass@k, pass^k and their intervals are null.

The user-error table lists telecom 3/50 critical and 5/50 benign errors; its caption says no critical errors, contradicting the table and accompanying text. Treat the table's 6% critical rate as the reported count, not zero; it is not a simulator accuracy estimate established here. Different domain populations also prevent attributing lower error solely to tool coupling. Four repeats and a tiny selected pilot would yield wide uncertainty and cannot establish leaderboard generalization.

## Transferable ideas for EDA

Adopt versioned state transitions, typed tool contracts, separate artifact/constraint ownership, and invariant-based terminal checks. Initialize from a pinned design/checkpoint; record every tool action plus observed output; independently recompute legality, equivalence and physical objectives. Negative controls should include stale checkpoints, missing final tool steps, contradictory logs and invalid constraints. Keep timeout/tool failure separate from correctness, and require concrete actions for escalation/hand-off when state alone cannot certify it. Do not invent a human simulator for autonomous EDA: the useful transfer is stateful verification and controlled access, not conversational role-play. A shared implementation bug can affect both reference solution and evaluator; independent invariants remain necessary.
