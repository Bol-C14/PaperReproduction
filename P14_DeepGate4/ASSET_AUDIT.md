## What the architecture route preserves

Code maps `tf_arch='sparse'` to 12 GAT transformer layers over global virtual edges, uses the DeepGate2 tokenizer, structural encodings, gate/graph task heads and CPU histories. The trainer loops over cone levels then mini-batches, retrieves prior embeddings and marks updated gates. This is enough source to study the intended mechanism without substituting TRACE or replacing it with an unrelated GNN.

The shipped launch script selects **DAGformer**, not sparse DG4, and uses mini-batch 256. `--pretrained_model_path` appears in it, but the tokenizer's preload call is commented out; `main.py` loads the full model only via `--dg4_path`. Therefore the script is not evidence of pretrained DG4 inference. `main.py` also passes the training set as both train and validation during training. `--is_test` runs embedding-only inference; it does not reproduce task-quality tables. [Launch](https://github.com/zyzheng17/DeepGate4-ICLR-25/blob/85e20742a2d4702426f94e86666cdcdb408fba8a/run/train_large.sh), [entrypoint](https://github.com/zyzheng17/DeepGate4-ICLR-25/blob/85e20742a2d4702426f94e86666cdcdb408fba8a/src/main.py), [config](https://github.com/zyzheng17/DeepGate4-ICLR-25/blob/85e20742a2d4702426f94e86666cdcdb408fba8a/src/config.py).

Concrete static integration cautions: the sample path does not trigger a named validation split, so the default validation set is empty; `Trainer` calls `torch.cuda.set_device` and forces CUDA despite the config's CPU fallback. In `dg4.py:445–446`, both history scatter expressions consume `hf_tf`, including the structural history assignment. These are observations requiring checking against intended behavior, not runtime-validated defects or claims about the paper's private experiment code. The loader replaces mismatched and missing tensors with current model tensors and uses `strict=False`, so “loaded successfully” would be insufficient evidence of checkpoint compatibility.

**One testable gap/control, proposed only:** establish a complete checkpoint-to-sparse-DG4 parameter coverage manifest (names, shapes, dtypes and trained-vs-initialized status) before interpreting outputs. Control: require all tokenizer, sparse-transformer, structural-encoding and relevant task-head tensors to match; report every dropped/missing/reinitialized tensor. This distinguishes a real released DG4 inference route from a tokenizer-only or partially initialized route. No such test was run.

## Systems acceleration is a separate route

The inspected commit contains no `.cu`/`.cuh` source, CUDA extension setup/build entry, custom fused binding or explicit Fused-DeepGate4 selection. The actual sparse implementation imports PyG **GATConv**; tokenizer aggregation uses ordinary PyG message passing/softmax. Requirements listing Triton is not a released DG4 Triton kernel. Source coverage includes the complete tree and text-source searches for fused/kernel extension references. This confirms the custom path is not in this tree, while external availability stays unverified.

The paper's specialized execution mechanism targets AIG in-degree 1/2, redistributes feature work across CUDA threads and skips trivial one-input softmax. An unfused port can preserve mathematical architecture subject to equivalence checks, but cannot establish those GPU performance gains. A CPU functional port cannot validate GPU speedup. Matching timing requires the actual fused implementation or a separately labelled reimplementation, same weights/graphs, numerical equivalence and matched GPU measurement boundaries. No port or benchmark was made.

## Resources and fidelity boundaries

[Paper, §§4.1–4.4, Tables 1–3 and Appendix A.1](https://proceedings.iclr.cc/paper_files/paper/2025/file/d75f561eaaf2cb754bc8d7e36d8af362-Paper-Conference.pdf): training uses one A800, 200 epochs, batch 1, mini-batch 128, hidden 128 and Adam at 1e-4. Table 1 reports DG4 7.37M parameters and 7.53G training memory. Table 3 gives unfused/fused inference memory 479/233 MB (ITC99), 130/91 MB (EPFL). These are workload peaks, not whole-machine minima. Graph examples span 1,861/10,502-node ITC99 validation designs, 84,742-node mem_ctrl and 402,193-node handmade image processing; larger scaling inputs duplicate the latter to ~800K/1.6M nodes. Embedding-only scaling drops task heads. A800 VRAM SKU, exact software/driver and elapsed pretraining time are unspecified in inspected material.

Static resource calculation from release code: two 10,000,000×128 and two 1,000,000×128 float32 CPU histories require **11,264,000,000 bytes (~10.49 GiB)** before masks, graph objects and activations. `History` requests pinned host memory and initializes it eagerly. Thus tiny samples still have a substantial host allocation as shipped. For future planning only, allow **32 GB host RAM** and a compatible NVIDIA CUDA GPU; **16 GB VRAM is a conservative sample/unfused starting budget**, not a verified minimum or performance guarantee. Full baseline comparisons can require far more memory. No environment GPU or VRAM availability was established and no CUDA probing was performed.

Dependencies: requirements pin torch 2.0.1 and PyG 2.4.0, but compiled graph wheels have `pt21cu118` suffixes; resolve this PyTorch/CUDA ABI mismatch before installation. `deepgate` is imported yet not pinned in the requirements; the README directs users to [python-deepgate](https://github.com/zshi0616/python-deepgate), whose inspected setup identifies version 2.0.1 without a dependency lock. Eager baseline imports can add GraphGPS/DAGformer requirements even for sparse DG4. Installation was not attempted.

## Licenses, access and stopping state

The pinned DG4 tree has no standalone LICENSE/COPYING file and README does not state separate code, sample-data or checkpoint terms. Treat these terms as unspecified; public readability does not establish a license. `python-deepgate` setup does not declare a license; its root `LICENSE` URL returned 404, which does not establish absence of all possible license notices. EPFL's repository declares MIT, which does not confer rights on DeepGate4 code or weights. No license was accepted and no gated assets were requested.

Web retrieval could not render several GitHub directory pages; the public Git tree provided the file inventory through the normal Git transport. No 403 or authentication gate was bypassed. No training corpus, checkpoint payload, large asset collection or external API was used. The remaining barriers are technical/provenance/terms uncertainties, not an approval denial. Audit complete; stop here.
